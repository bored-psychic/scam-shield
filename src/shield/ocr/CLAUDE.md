- OCR: coloured links in dark mode (2026-10-17, `reader._coloured_ink`, tests O9 + O13, `src/ocr_sweep.py` -> `reports/ocr_sweep.md`; contract, router, models, frontend untouched): the invert step turns a mid-brightness link colour into a light grey and Tesseract drops it (iOS Messages dark blue (10, 132, 255): luma 109 vs 38; plain (0, 0, 238): 27 vs 40; the real Google Messages link (40, 105, 220) on a (32, 33, 37) bubble). In the inverted image the darkest channel is 255 minus the BRIGHTEST original channel, so a coloured stroke stands out there while luma flattens it; swapping it in for luma erases white text on saturated bubbles, so it is a supplement: dark branch only, `grey` darkened by (top-hat of that channel minus top-hat of luma), box 15 px at 1080 wide (`_stroke_box`); only where the MEDIAN paper level (quarter scale, ~44 px) has every channel >= `PAPER_MIN` 170, i.e. a bubble dark in every channel (a closing rides up to the JPEG noise peak and let a teal bubble through at 128 and at 170); only within 1.5 boxes of a stroke whose extra ink peaks >= `INK_PEAK_MIN` 40, everywhere else byte-identical to luma; a weaker stroke is lifted to `INK_FLOOR` 110, never a stronger one (x2 gain bloats strokes). Chroma (max - min) was measured and rejected: JPEG stores it at half resolution and it smears thin strokes (real screenshot 20 of 64 re-encodings vs 50 of 64; 83-90% on a JPEG colour sweep). Real fixture `tests/fixtures/real/jio_kiwi_dark.jpg` (the user's own Android dark-mode Jio promo SMS; dev set, never test set; Tesseract 5.5.3, and a clean 5.3.4 built in a scratch dir with Homebrew tessdata): with the original conversion the link line is lost in 0 of 64 reads (16 re-encodings x 2 builds x `eng` / `eng+hin+kan`), with the step the link (host t.jio, a `/` path) is recovered in 50 of 64 and the link CER goes 1.000 -> 0.321; O13 asserts the link, the lines `Dear User` / `Claim now` / `JioCoupons`, verdict Likely scam (as for the typed text) and that the Link panel lists it (it shows `https://t.jio/`: OCR puts a space after the first slash). **The reported "link still missing after the first fix" did not reproduce:** the first version read the link in all 4 engine / language combinations (a stale server is the likeliest cause, not verified), and the offered mechanism (darkest channel = red) is not what the code computes. - OCR link repairs (D19b, 2026-10-17, `shield.ocr.reader.repair_links`, test O10, 27 cases, each also idempotent): two more narrow shapes beside the old `https:/Awww.` one. (1) A space beside the colon: `https :/Awww.bet365.com/`, `http : /Aexample.in/x` -> scheme + `://`; only with a space next to the colon, a `www.` or a lower-case dotted host right after, and one stray character from `A ( [ | ! \` (a capitalised `https :/Example.in` keeps its `E`); the unspaced `https:/sbi.top/x`, a bare `https :/A` and `ratio 3 :/A` stay as they are. (2) A space after a dot inside a host: `https://t. jio/TIOCPN/x` -> `https://t.jio/TIOCPN/x`; only inside a token that already starts with `scheme://`, only before 2-24 lower-case letters (dotted names allowed) and then `/` or the end of the token; **beyond the first spec**, without a `/` only when the part before the space is a single label (`https://t.`, `https://www.`), so `Visit https://ok.com. then pay` is not glued into `ok.com.then`. Why narrow, and what is deliberately not repaired: `docs/decisions/README.md` D19b.
